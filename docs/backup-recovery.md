# 数据集中在服务器：先准备能恢复的备份

**手机和 Windows 是控制入口，服务器才保存项目、必要会话状态与持久文件。** 手机看过文件、应用缓存过几条消息，不等于它有服务器数据的完整副本。

## 可能一次影响多个项目

- 单块硬盘损坏、存储控制器或文件系统故障，可能让多个项目同时不可读。
- 误删、错误的脚本、错误的清理范围或被盗的写权限，可能同时影响共享区和多个项目。
- 跨项目调用增加便利，也可能扩大误操作范围；Agent 的目录权限仍须按项目授权。
- 容器、RAID、同一服务器上的快照或另一目录有各自用途，但不单独保证应对整机丢失、存储损坏和误删。

因此，一台控制服务器之外要有独立的备份位置；不必再运行第二套 Agent，但必要数据要有服务器以外的可恢复副本。

## 优先保护什么

| 数据 | 建议 |
|---|---|
| 项目源码、提交历史、必要配置和任务结果 | 带版本备份；Git 远程只覆盖已经提交并推送的内容 |
| 持久会话、事件与消息数据库、请求回执 | 一致性备份；保留恢复原请求状态所需的关联文件 |
| 用户主动保存的文件、共享项目中的工作副本 | 纳入项目备份；不要把它们当作可删除上传缓存 |
| 必要认证与恢复材料 | 独立加密存放，最小访问权限；不要放入公开仓库 |
| 可重新生成的构建缓存、确认无引用的临时副本 | 可以排除；依据引用和归属，不能只按年龄清理 |

对正在写入的数据库使用其一致性备份机制，或在协调停写后取一致快照。SQLite 可使用官方[Online Backup API](https://www.sqlite.org/backup.html)；复制一个正在变化的数据库主文件并不能保证得到完整状态。

## 最小备份方案

1. 列出必须恢复的数据、可以接受的最大丢失时间和目标恢复时间，据此选频率与保留期。
2. 将带版本副本放到独立机器、存储服务或独立介质；保留能抵抗误删的历史版本。
3. 加密传输和存储；备份账号与 Agent 日常写入权限分开，避免 Agent 可以删除所有历史备份。
4. 根据需要再保留离线或不可变副本。CISA 建议保留离线加密备份并定期验证恢复。[官方指南](https://www.cisa.gov/stopransomware/ransomware-guide)
5. 监测备份失败、容量与保留期；预算页的 $3 只是教学占位，不代表已经配置备份或满足你的容量。

## 真正验一次恢复

在独立测试目录或替代服务器恢复，核对文件清单、项目能否打开、数据库完整性以及必要会话与回执。恢复环境先断开真实模型和发布权限，不能把历史“处理中”的写入自动重发。

记录最近一次成功恢复、覆盖范围、未备份项和恢复用时。单纯看到“备份任务成功”不是恢复验收；本公开蓝图也不证明读者自己的备份已经可恢复。

发生事故时，先停止继续写入、保留原存储与证据，再选择已验证的恢复点。不要先对受损磁盘运行未经验证的修复或让多个 Agent 同时改写它。
