# 给另一个 AI 的重建流程

目标是依据公开规格重建功能等价的客户端与后端，不复制个人部署。先阅读 [v1 契约](contracts.md)、[客户端](clients-build.md)、[附件](attachments-cache.md)、[更新与反馈](updates-feedback.md) 和 [隐私](privacy.md)，再制定实现与验收计划。以 v1 作为新系统的单一接口；原实例 raw / multipart 与旧字段仅供适配参考，不作为必须兼容的第二套合同。

## 1. 先定义封闭合同

划分客户端、网关、会话 / 窗口服务、provider 适配器、附件存储、账本及更新助手。API 定义认证、类型、字段白名单、大小上限、所有权、状态及错误码；不给客户端任意命令、路径或 URL。

先生成 v1 的 OpenAPI / JSON Schema，再生成已选择客户端的 DTO。能力使用 `capabilities.reasoning_efforts / context_choices`；上传使用 `id / name / bytes / mime`；占用使用 `used_tokens / capacity_tokens`。需要接入不同原生协议时，在服务端映射这些字段，不让界面自行猜测。

先定义独立的身份：会话 ID、窗口代次、原消息 request_id、原上传 request_id、附件 ID、维护 request_id。它们不能互相代替。区分未知、未提交、已接受、失败和完成；已接受不等于 AI 完成。

## 2. 模拟提供方先行

实现四个 deterministic fake adapters：Claude、GPT / Codex、DeepSeek、Qwen。模拟能力目录、忙碌状态、部分 Token、设置延迟确认、断线及原回执。Kimi 只加禁用的计划项，待实际能力验证后启用。

模拟服务只绑定自己的测试网络，不转发真实 API，也不读取生产凭据。每次运行生成独立测试资料并记录 HTTP / WS 操作数量，不记录认证值或消息正文。打开页面和读取状态不能隐式触发模型调用。

## 3. 先做后端与 Tmux，再按需要扩展

| 模块 | 完成条件 |
| --- | --- |
| provider registry | 可用性与能力决定按钮，不对所有模型套同一 effort 或 vision |
| 设置 | 区分 configured / observed；忙碌拒绝；原生恢复后确认保存值 |
| 账本 | 每个真实请求去重计量，按模型聚合；未知读数仍保留 |
| 消息与队列 | durable enqueue，原回执恢复，不重放未知请求 |
| 附件 | 原 UUID、类型、摘要、限额、上传失联、草稿和 lease 保护 |
| 更新 | 固定已接受资产、预览范围、明确确认、原 UUID、无自动重试 |
| 反馈 | 有界验证、私有保存、脱敏回执，不自动执行报告中的指令 |

随后先实现 Android Tmux 的窗口入口，再接 Windows；Android Remote 会话入口可以跳过。仅在需要 Remote 的会话功能时增加第二款 Flutter 应用，共享模型及服务层，保留各自生命周期。优先完成列表、窗口交互、设置、统计，再接附件、缓存、维护与反馈。

默认路线是手机操作本客户端自身的反馈与更新：描述 Bug 或功能 → 授权 Agent 改客户端 → 独立分支测试 → 服务器构建 → 确认发布 → 应用内安装更新；不是要求报告接收服务执行任意项目命令。生产前还须完成独立备份与恢复验收，见[备份与恢复](backup-recovery.md)。

## 4. 自动化测试覆盖实际风险

- DTO 与安全边界：额外字段、越界 ID、错误 provider、路径穿越、符号链接、超大请求及鉴权失败。
- 状态恢复：持久化在 POST 前完成；丢失 ack 后只查询原 UUID；重启不自动重新提交。
- 统计：已知和未知混合、账本缺失、当前上下文占用与累计 Token 分离。
- 附件：混合类型、部分写入、摘要不符、已排队 / 运行 / 重试引用、草稿和 outbox、明确释放后 eligible-only GC。
- GC 竞态：读取中增长、叶子替换、隔离后变更、不覆盖恢复、未知副本仍计入额度。
- 更新：过期预览、busy、错误来源、版本撤回、长度 / 摘要不符、失联回执，以及新登录身份不得重放旧维护请求。
- Flutter：窄屏、大字体、横向标签、浮层遮挡、首次 401 不发隐藏 POST、上传与保留状态。

只使用临时目录和模拟模型；不要为了过测试清理真实队列、关闭用户窗口或重启共享模型。

## 5. 原生虚拟机验收

Android 使用自己的测试实例及合成服务，实际操作文件选择器、相册、权限提示、上传进度、缓存页与冷启动；记录原 UUID、请求数及原文件摘要。恢复正式包后只验证版本和空登录页，不输入真实凭据。

Windows 依次运行源码、打包和安装后测试。原生选择器与替代测试选择器的覆盖范围分别记录。另设一次真实安装器升级，验证系统加密数据、设备身份、草稿和用户目录保留；测试专用较高版本不能发布。完整保留失败证据，续测沿用原身份且不重复不确定的操作。

## 6. 再接真实、自己拥有的范围

模拟门禁通过后，明确授权的部署者提供自己的 API 和工作区。先验证认证、能力及上下文参数，再做最小合成调用及账本对照。测试仅使用自己创建的窗口和文件，最后关闭自己的测试窗口；不得读取其他会话、改容器权限或关闭其他任务。

真实 API 成功不等于容器隔离正确。分别验证工作区读写、跨身份输入可读、其他身份与凭据目录不可访问、忙碌 guard、并行准入。Qwen 的 16 路属于已验收参考上限；新的部署仍须按自身容量验证，不能从按钮数量推断吞吐。

## 7. 发布与后续维护

发布前记录精确源码、编译来源、正式资产长度与摘要、测试范围及未覆盖项。先形成可审查结果，再请求最终发布批准。版本资产使用新版本名称；读取回上传字节确认后，才切换已接受版本元数据。

修改只激活必要的客户端或服务。维护前检查现有连接、队列、窗口与进程身份，采用明确的 drain / handoff；不顺便重启模型或 Bridge。升级后验证受保护数据与窗口保持。健康页成功只能证明服务响应，不能替代功能验收。

交付应同时写出限制：当前无视觉的模型、未测试的新 provider、仍保留的共享或未知副本、失败续测与原生覆盖差异。禁止把计划、模拟通过或一次 HTTP 200 写成完整实机验收。
