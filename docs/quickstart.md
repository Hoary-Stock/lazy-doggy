# 从一台服务器开始

[返回总览](../README.md) · [AI 任务书](../AI_BUILD_PROMPT.md)

## 1. 选择最小版本

先做 **Android Tmux → 一个服务端 → 一个模拟 Agent**，再按需要加 Windows。Android Remote 是可跳过的早期会话路线，不是完成最小系统的前提；两款手机应用并用的缘由见[客户端取舍](clients-build.md)。服务器上运行控制服务和 Agent，客户端只负责输入、显示和控制。暂不引入 GPU、第二台控制机器或多 Agent 调度。

先阅读[非商用许可](licensing.md)。[白板示例](whiteboard-example.md)可用于理解最小数据流，但不能直接部署，须先由自己的 AI 审查、修理并按验收清单补全。

外部 API 路线通常可以把控制服务和适配器放在一台 CPU 服务器上。原生 CLI 路线还需要安装 CLI、按其官方方式登录，以及留出多个进程的内存。4 GB 只是轻量起步配置建议，不是实测容量承诺；多个重型 CLI、较多窗口或容器可能需要 8 GB 以上。

## 2. 准备自己的基础设施

1. 安装维护中的 Linux 发行版，创建普通服务用户，设置独立的数据目录。
2. 购买或使用已有域名，例如 `agent.example.org`，将 DNS 指向自己的服务器。
3. 设置反向代理和 HTTPS，内层服务只监听回环地址或受控 Unix socket。
4. 通过部署端的秘密注入机制配置自己的账号/API Key；客户端不保存上游模型密钥。
5. 建立独立测试目录和备份位置，默认没有读取其他项目、其他 Agent 私有目录的权限。

TLS 可使用自动续期的免费证书。域名、服务器和模型分别收费，详见[成本](costs.md)及[来源](sources.md)。

## 3. 按模块实现

```text
your-project/
  server/             # 鉴权、会话、事件、上传、反馈与更新元数据
  adapters/           # mock、CLI、外部 API
  clients/
    android-tmux/     # 窗口控制入口
    android-remote/   # 可选的结构化会话入口，可以不实现
    windows/          # 桌面入口
  contracts/          # 请求、回执、能力、用量的 schema
  tests/              # 模拟传输与故障测试
  ops/                # 部署配置占位模板和验收工具
```

先实现鉴权和模拟会话，再实现可恢复事件和普通文件上传。每次写入都有稳定请求编号；超时后先查原回执。接入真实 CLI/API 时，能力由适配器明确声明，而不是依据模型名称猜测。

具体工作顺序见 [AI 实施顺序](ai-build-playbook.md)，接口字段与状态机见 [接口约定](contracts.md)。

## 4. 连接客户端

先在 Tmux 使用自己的 HTTPS 服务地址登录，Windows 随后复用服务。依次验收发送、接收、断网恢复、上传、移除附件和缓存保护。再添加多个 Agent 的筛选、思考/上下文控制和真实 Token 统计。Android Remote 仅在需要其会话功能时另外实现。

手机问题反馈先只进入私有队列。开发者或 AI 根据复现信息定位候选修复，经过测试和必要确认后发版。应用内更新只从受信来源读取元数据，下载后核对摘要；Windows 需保留登录和草稿，Android 需延续签名证书。

## 5. 验收后开放访问

完成 [验收清单](acceptance.md)，再配置正常使用的账号和分发入口。先用合成数据完成原生 Android/Windows 测试；手机控制界面不能直接变成任意 root shell。备份应覆盖配置与必要持久状态，临时附件和未知用户文件按各自策略处理。

最终你得到的是自己的实现和账号体系，本仓库不会提供原作者的服务入口或二进制。

## 6. 先备份，再依赖它工作

项目、会话与必要文件集中在服务器；客户端不是它们的完整副本。存储损坏可能使多个项目同时丢失数据。生产使用前准备独立、带版本的备份，限制 Agent 对备份的修改权限，并在另一处测试恢复。详见[备份与恢复](backup-recovery.md)；当前预算中的备份金额只是教学占位，并不代表已经买到足够容量或保护。
