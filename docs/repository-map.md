# 文档与模块地图：从 Tmux 开始搭建

[返回总览](../README.md) · [快速开始](quickstart.md) · [AI 任务书](../AI_BUILD_PROMPT.md) · [网络链路](network-path.md)

## 1. 默认路线：Tmux → Windows → Remote 可选

第一次搭建，建议先完成 **Android Tmux 客户端 + 服务端窗口控制**，再增加 Windows 客户端。只有需要更完整的结构化会话、队列、检查和管理体验时，再实现 Android Remote；新搭建者可以直接跳过它。

Android Remote 是作者最初的探索路线。作者起初没有程序开发背景，在设计过程中绕过一些弯路，逐渐积累了较多功能。按作者现在的日常取舍，Tmux 更顺手；这是使用经验，不是性能基准或所有人的统一结论。

作者仍将两者并用，因为希望 Tmux 保持精简，把部分会话和管理功能放在 Remote。文档保留 Remote 的规格是为了提供选择，不要求读者先重做一遍早期探索。下面涉及 Remote 的实现条件，仅在选择该产品时适用。

## 4. 新项目的建议模块布局

这是供独立重建使用的建议目录，不是本公开仓库实际提供的程序。名称可以调整；模块职责与 v1 边界要保持一致。

```text
your-project/
  server/
    auth/                 # 应用身份、撤销、限流
    windows/              # 原生窗口清单、代次、broker、终端票据
    sessions/             # 可选逻辑会话、runner、持久队列
    events/               # journal、seq、分页、补读
    adapters/             # mock 与各 provider 协议转换
    attachments/          # 流式上传、回执、hold、lease、有限 GC
    usage/                # 真实请求账本与按模型汇总
    control/              # 设置、维护、发布元数据、客户端反馈
    tests/                # 模拟传输和独立临时数据
  clients/
    android-tmux/         # 第一入口：已有窗口
    windows/              # 第二入口：Electron 与固定网关
    android-remote/       # 可选：更完整的结构化会话体验
  schemas/                # v1 DTO、OpenAPI、JSON Schema
  acceptance/             # 合成服务、原生驱动与私有验收结果
  ops/                    # 无凭据的部署模板与维护工具
```

认证材料、运行状态、备份密钥、真实日志和用户文件均在仓库之外。测试结果也先按私有材料处理；只有经过独立审阅的合成内容可用于公开展示。

## 5. 模块之间传递什么

| 模块 | 输入 | 输出 / 持久记录 | 主要约束 |
| --- | --- | --- | --- |
| 客户端 | 用户文本、系统选择器授权、确认 | 持久草稿、outbox、原请求 UUID | 不保管模型密钥，不因断网丢草稿 |
| TLS / 鉴权入口 | 固定 HTTPS / WSS 请求 | 已授权范围、有限错误 | 没有任意 URL 或命令代理 |
| 窗口服务 | 目标不透明 ID、窗口代次与一次输入 | 原生交付证据、事件 | 输入前复查身份、空闲与交互问题 |
| 可选会话服务 | 逻辑会话与持久消息 | 队列、native 映射、runner 状态 | 网络订阅者不拥有任务生命周期 |
| Agent 适配器 | 已验证的模型设置与受控输入 | 原生事件、能力和实际用量 | 不同模型独立身份，缺失能力明确禁用 |
| 附件服务 | 有界原始字节、显示名与 UUID | SHA、opaque ID、上传回执、引用 | 不执行文件，不把文件名当路径授权 |
| 统计服务 | 真实模型请求记录与原生读数 | 去重账本、完整性、窗口观测 | 上下文、累计 Tokens、订阅额度分开 |
| 更新与反馈 | 状态读取、显式预览 / 确认、有限报告 | 原回执、已接受版本、私有反馈 | 读状态不更新，反馈不直接执行修复 |
| 备份 | 明确持久数据与一致性快照 | 独立加密版本及恢复证据 | Agent 日常写权限不控制全部历史备份 |

公共接口以 [contracts.md](contracts.md) 为唯一新合同。附件文档中的原实例 raw / multipart 字段只是映射参考，不要求客户端同时实现两套接口。

## 6. 四条重要数据流

### A. 从手机发送到原窗口

`选择窗口 → 保存请求 UUID → 鉴权 → 验证原窗口代次与状态 → 交付一次 → 保存证据 → 返回 / 补读事件`

Tmux 与 Windows 可围绕这条线做最小系统。单纯调用“发送按键”返回成功不证明 Agent 已接收；失去确认先查原回执。不要因重新打开页面而另建一份任务。

### B. 从手机附件到 Agent 可读输入

`系统选择器 → 应用私有快照 → 摘要与原上传 UUID → 上传一次 → 核验回执 → 取得引用 / lease → 授权工作区受控副本 → 一次消息`

`file_ids` 与 `image_ids` 分开；普通文件不意味着视觉理解。模型没有图像能力时禁用视觉入口。私有清理只处理完整盘点后明确释放、无引用且未改变的副本；原件、共享项目副本、结果和未知项保留。

### C. 设置与统计回到界面

`能力目录 → 选择允许的 effort / 上下文 → fresh idle guard → configured 回执 → 原生 observed → 界面分别展示`

另一路是 `真实模型请求 → 去重账本 → 按模型 / 日期 / 窗口汇总`。窗口当前占用不能拿累计 Tokens 代替，未知用量不能显示成零。Qwen 的参考 16 路是服务器共享准入预算，不是每个客户端各开 16 路；新部署仍需验证实际容量。Kimi 保持计划项，未验收不启用。

### D. 客户端问题反馈到新版

`客户端 Bug / 功能建议 → 用户检查截图与复现步骤 → 私有有界报告 → 开发者 / AI 定位候选修复 → 独立分支与测试 → 原生验收 → 确认发布`

这里的反馈指 **Tmux、Windows 或 Remote 客户端本身的问题与功能需求**，不是让应用自动诊断用户业务项目的 Bug。报告接收不保证已经 AI 评审、自动修复或发版；业务项目排查仍需另外的任务和授权。

## 7. 哪些功能可以后做

| 阶段 | 建议范围 | 可暂缓 |
| --- | --- | --- |
| 起步 | mock、认证、Tmux 窗口列表、一次发送、原回执、重连 | Remote 会话导航、多机网络、GPU |
| 日常使用 | 一个真实适配器、普通文件、保护缓存、窗口设置与真实统计 | 更多 provider、窗口模型分析 |
| 桌面 | Windows 窄 IPC、系统凭据保护、附件与应用更新 | 非 Windows 平台 |
| 扩展 | 按需 Remote、更多已验证适配器、Agent 更新与受控检查 | 未验证 Kimi、自动修复工作流 |

即使不做 Remote 客户端，Windows 所需的后端能力也应由独立服务模块提供，不要求用户先安装另一个手机 App。Qwen Code 更新未来实例与 DeepSeek 等运行时维护的作用范围不同，详见[更新与反馈](updates-feedback.md)；它们不是最小联网闭环的前置条件。

## 8. 每一步怎样算完成

先保存可审查的 schema、源码差异和模拟测试结果，再接自有真实范围。手机必须实际验系统选择器、窄屏 / 大字体、断线与冷启动；Windows 分别验源码、打包、安装及升级后数据保留。所有不确定写入保留原身份，不因测试续跑而重复提交。

发布前还需证明下载字节、正式签名 / 身份、持久数据与现有窗口保持。备份不止“任务成功”，应完成一次独立恢复。服务器集中存储带来大量数据同时丢失的风险，[备份与恢复](backup-recovery.md)是部署门禁，不是将来有空再做的缓存功能。

已采用组件、推荐新设计、可选路线和未验证能力分别标记。阅读完成不等于已获部署、模型调用、停止窗口或发布权限；这些动作由搭建者在自己的环境明确授权。
